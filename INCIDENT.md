# Incident runbook

What to do when a vulnerability affects the editor's demo environments. Pick the playbook that fits, or combine them: mitigate in the images, and take the environment offline until the mitigation is live.

## 1. PHP vulnerability in the Drupal or TYPO3 image

The Drupal and TYPO3 demo images are built from the official PHP-based images in `app/drupal/Dockerfile` and `app/typo3/Dockerfile`. When a PHP vulnerability is published before patched base images are available, override the affected PHP settings in the image.

1. Add a `RUN` step to both Dockerfiles that writes an ini file to `/usr/local/etc/php/conf.d/`. Prefix the file name with `zz-` so it loads last and wins over earlier ini files.
2. Chain a `php -r` check for each setting that matters, so the build fails when a setting does not take effect.
3. Open a PR and merge it to `main`. The Docker Drupal and Docker TYPO3 workflows then publish the new images, which the demo environments pick up through Flux.

### Example: CVE-2026-109618 / CVE-2026-109619 (October 2026)

`app/{drupal/typo3}/Dockerfile`:

```dockerfile
RUN { \
        echo 'session.upload_progress.enabled = 0'; \
        echo 'fatal_error_backtraces = 0'; \
        echo 'memory_limit = -1'; \
        echo 'post_max_size = 8M'; \
        echo 'upload_max_filesize = 2M'; \
        echo 'expose_php = 0'; \
        echo 'display_errors = 0'; \
    } > /usr/local/etc/php/conf.d/zz-cve-mitigation.ini \
    && php -r 'exit(ini_get("session.upload_progress.enabled") === "0" ? 0 : 1);' \
    && php -r 'exit(ini_get("fatal_error_backtraces") === "0" ? 0 : 1);' \
    && php -r 'exit(ini_get("memory_limit") === "-1" ? 0 : 1);' \
    && php -r 'exit(ini_get("expose_php") === "0" ? 0 : 1);' \
    && php -r 'exit(ini_get("display_errors") === "0" ? 0 : 1);'
```

## 2. Taking demo environments offline

The demo environments run on the NL Design System Kubernetes cluster, managed with Flux from the [`nl-design-system/infra`](https://github.com/nl-design-system/infra) repository. We do not have direct cluster access, so every change goes through a PR on the `dev` branch of that repository. Flux syncs `dev` every minute, so a merged PR takes effect within a few minutes.

### Option A: scale down the editor apps (default)

Takes only the editor demo apps offline.

In `flux/editor-main/editor-drupal.yaml`, set the Deployment in the `ResourceSet` to zero replicas:

```yaml
- apiVersion: apps/v1
  kind: Deployment
  metadata:
    name: editor-drupal
  spec:
    replicas: 0
```

Do the same for the TYPO3 environment. Leave the `Service` and `HTTPRoute` in place; the hostname then returns `503`.

**Restore:** set `replicas` back to `1`. The database runs on an `emptyDir` volume, so the demo starts with fresh content.

### Option B: scale down the Istio gateway (kill switch)

Takes **everything** behind `*.review.nlds.delta10.cloud` offline: all editor environments, other review apps on the cluster and the Flux webhook receiver. Flux keeps polling Git, so the restore PR is still applied.

The gateway Deployment (`external-gateway-istio`) is generated by Istio from the `external-gateway` Gateway in `flux/istio-gateway/external-gateway.yaml`. A `HorizontalPodAutoscaler` with `minReplicas: 2` keeps it running, so scaling to zero takes two changes in that file:

1. Remove the whole `HorizontalPodAutoscaler` resource named `external-gateway`: everything from `apiVersion: autoscaling/v2` up to the next `---` separator. Flux prunes it from the cluster, so it stops scaling the gateway back up.
2. Set the generated Deployment to zero replicas, through a ConfigMap referenced by the Gateway (see [Istio: Gateway API deployment customization](https://istio.io/latest/docs/tasks/traffic-management/ingress/gateway-api/#automated-deployment)). Add the ConfigMap as a new resource at the end of the file:

   ```yaml
   ---
   apiVersion: v1
   kind: ConfigMap
   metadata:
     name: external-gateway-options
     namespace: istio-gateway
   data:
     deployment: |
       spec:
         replicas: 0
   ```

   Then add `infrastructure` to the `spec` of the existing `external-gateway` Gateway at the top of the file. Do not add a second Gateway:

   ```yaml
   spec:
     gatewayClassName: istio
     infrastructure:
       parametersRef:
         group: ''
         kind: ConfigMap
         name: external-gateway-options
     listeners:
       # ...unchanged
   ```

This setup has not been tested on our cluster. Ask the maintainer of the infra repository to review the PR before merging.

**Restore:** revert the PR.
